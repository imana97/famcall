CANCELLATION WHILE OUTGOING SETUP IS PENDING
Outgoing attempts now own their request UUID before contacting the server.
End Call updates the screen immediately and persists that ID even before a
CallRecord exists. Late server/native completions cannot bind or navigate the
cancelled attempt; a late native UUID is closed independently of any newer call.
An uncertain create response also queues cleanup, since a timeout does not prove
the server failed to create the call. A newer Firestore call state is preserved
instead of being overwritten by an older callable response.

The backend transaction records an end-before-create receipt under the caller's
own user record. startCall reads it in the creation transaction. Other users'
receipts cannot cancel a guessed request ID, and existing-call membership checks
still apply. Receipts are server-only, expire with the 90-day history retention,
and are removed by account deletion. A transactional deletion check prevents a
concurrent deletion from being followed by a new receipt. Deployment must include
the cancelledStarts TTL configuration; no production deployment was performed.

The outbox now processes an end intent added during an existing delivery. Its
previous single snapshot could leave that intent queued until another network
event. The controlled regression delivered only the first intent on the old code
and both intents with the fix. The final backend suite also verifies deletion of
cancellation receipts and denial of the deleted identity.

INCOMING-CALL REGISTRATION RECOVERY
A source review after the hosted tests found that a failed registerDevice upload
had no timer or network/foreground retry. Incoming-call push could therefore
remain unavailable after a brief outage until another token event or app restart.
The client now retains the latest native token, serializes uploads, retries at
5/15/30/60 seconds, and starts a fresh bounded attempt when connectivity returns
or the app becomes active. It stops queued work when the account changes or the
provider is disposed. It does not promise background execution while the OS has
suspended the app.

A persisted installation sequence orders token changes across restarts and
concurrent preparations. The backend binds each upload to its originating account
and ignores older sequences, preventing a delayed request from replacing newer
registration state. APNs/FCM rejection cleanup compares the exact document
version: an old rejection cannot remove a refreshed token. An invalidated record
retains its sequence until normal expiry and removes the rejected token, so a
late duplicate upload cannot resurrect it. This changes the registerDevice
contract; the matching backend and app must ship together. No public app has
been released with the earlier contract.

Seven controller tests cover upload failure/recovery, bounded retries, token
rotation during successful/failed uploads, missing token arrival, storage/native
failures, account changes and disposal. Two storage tests verify serialized,
persisted ordering, legacy installation reuse and write-failure recovery. Two
Auth/Firestore callable integration cases verify account binding, late uploads,
conflicting sequences, old rejection responses and invalidation/re-registration.

MEASUREMENT RULES
The audio lab injects generated speech into the emulator microphone and captures
the receiving emulator output. It never uses the computer's microphone. STOI is
an intelligibility estimate, not a MOS score, human listening result, or proof of
physical-device performance. Tests check the actual selected ICE candidate path.
Per-leg impairment settings must not be reported as end-to-end loss/latency.
Only completed, reproducible cases with valid source/capture signals count.

ADDITIONAL SIMULATOR FINDING
The iOS 26.5 simulator accepts reportNewIncomingCall, then its system call
service ends the call almost immediately (disconnect reason 55 / generic error).
Its logs also show failure to open the incoming-call system interface. This
reproduces without an active iOS Maestro flow. It is not counted as an incoming
call pass; validate the actual signed app on an iPhone before release.

STANDALONE IOS CONTROL — 7 NOVEMBER 2026 UTC
The independent native probe in e2e/ios-callkit-probe contains no FamCall,
Firebase or WebRTC code and performs no microphone/network work. The same probe
binary was tested once on each of two fresh, dedicated iPhone 16 Pro simulators.
Both accepted reportNewIncomingCall, then ended the call before probe cleanup:
44 ms after report completion on iOS 26.5 and 216 ms on iOS 18.6. Both system
logs failed to open facetime://?launchForIncomingCall=1; only the 26.5 log showed
reason 55. No user answered or ended the calls. Cleanup succeeded on both.

Three setup attempts are retained separately: a missing simulated identity
caused service rejection, and a restricted ad-hoc signing entitlement prevented
launch in two attempts. The corrected packaging matches Xcode's simulator
entitlement sections. The committed build script reproduced the exact binary
used for both valid observations. Source/binary/event/log hashes and manifests
are retained in .local/callkit-probe/audit.json. This isolates a simulator failure
from the app but does not prove physical iPhone calling or rule out other bugs.
